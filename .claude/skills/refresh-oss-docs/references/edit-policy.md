# Edit policy

How aggressively an editor may change a page depends on how much *editorial*
content that page carries. A mechanically-correct edit can silently destroy a
tutorial while being exactly right for a reference page.

## The four types

| Type            | Substrate         | Policy           |
| --------------- | ----------------- | ---------------- |
| **reference**   | hand-written .mdx | **Assertive**    |
| **how-to**      | .ipynb            | **Assertive**    |
| **tutorial**    | .ipynb            | **Conservative** |
| **explanation** | hand-written .md  | **Conservative** |

### Assertive

The snapshot signature is ground truth. Rewrite entries, update call sites,
adjust the surrounding steps so the page stays coherent and runnable. Add
reference entries for new symbols.

### Conservative

Make only the edits the API change *forces*:

- a renamed symbol or parameter → rename it
- a reordered argument → reorder it
- a changed default asserted in prose → correct the value

Nothing else. Do not restructure, do not rewrite narrative, do not "improve"
prose you happen to be passing through.

## Escalation

**Escalation is not failure.** A refresh that updates 8 pages and flags 2 is a
good outcome. One that silently rewrites all 10 is not.

Flag — do not edit — when:

| Type        | Flag when                                                    |
| ----------- | ------------------------------------------------------------ |
| reference   | never (the work is mechanical)                               |
| how-to      | the delta removes the feature the guide exists for           |
| tutorial    | the change alters *what the lesson teaches*                  |
| explanation | the concept being explained no longer exists                 |

A `symbol_removed` delta on a page is the most common escalation trigger: the
page is now *wrong*, not merely stale, and deciding what should replace it is an
editorial call, not a mechanical one.

## New symbols

Add a reference entry — that is the reference contract.

Do **not** author tutorials, how-tos, or explanations for new features. Whether a
feature deserves a page, and what that page should teach, is a human's decision.
New symbols with no existing mention are reported in the PR body as
"undocumented", and there they stop.

## Notebooks

If your work order names a `.ipynb`, edit the notebook. The `.mdx` beside it is
git-ignored build output regenerated by `make regen-mdx`; an edit there
evaporates.

Edit the `source` array of the cell the work order points at. Leave `outputs`
and `execution_count` alone — the verifier re-executes notebooks, and CI
refreshes outputs on merge.

## Both substrates

- Preserve frontmatter, custom prose, and hand-written examples.
- Match the surrounding style: comment density, naming, and idiom.
- Do not reformat lines you did not need to change.

## Code examples

Doc code is not uniformly checked, and the parts that are unchecked are not
marked as such. Know which surface you are standing on before you touch a
snippet.

| Surface                                        | Checked how                                     |
| ---------------------------------------------- | ----------------------------------------------- |
| `src/content/docs/oss/**` Python fences         | pyright, via `pnpm run test:python-snippets`     |
| `src/content/docs/oss/checks/**.ipynb`          | executed, via `tests/test_docs_nb.py`            |
| `giskard.checks` / `giskard.scan` API claims    | `docs/api-baseline/*.json`, via `test_docs_refresh.py` |
| `src/content/docs/hub/` — **everything**        | **nothing**                                     |

`check-python-snippets.mjs` hardcodes `src/content/docs/oss`, the notebook
harness only walks `oss/checks`, and `giskard-hub` is not a dependency of this
repo, so it cannot be imported, executed, or type-checked here. There is no Hub
API baseline. `hub/sdk/reference.mdx` is hand-maintained prose, not generated.

So on `hub/**` the only thing you can establish is that a snippet agrees with
`reference.mdx` — one hand-written page agreeing with another. If that page has
drifted from the shipped SDK, your snippet inherits the drift and every check in
this repo still passes.

### Two traps, both of which look like diligence

**Existence is not justification.** Confirming a parameter appears in
`reference.mdx` proves the edit is *valid*. It says nothing about whether the
edit was *needed*. `limit` and `offset` are real; a snippet that passes them,
assigns the result to a variable, and never uses it is still noise. Ask "does
this change earn its place?" separately from "is this symbol real?" — the second
question passing is what makes the first one easy to skip.

**Speculative correction.** Do not "fix" a working example because you infer it
is wrong. Inference is not evidence, and on an unchecked surface nothing will
contradict you. Check the page's neighbours first: they are the cheapest
available evidence and they usually already answer the question. An example
adding `include=["agent"]` to a `retrieve()` call was refuted by the `list()`
example ten lines above it, which read the same attribute with no `include` at
all.

### Rules

- **Adding** a line to an unchecked snippet is acceptable when a sibling
  operation in the same file already establishes the pattern.
- **Editing** an existing working example on an unchecked surface: don't. Flag
  it instead. You cannot verify it, and the example predates you.
- Every snippet must *do* something. Fences that construct a value and drop it
  teach nothing and are indistinguishable from a mistake.
- If a claim cannot be grounded in the page, a sibling page, or a baseline, it
  does not go in. Say so in your report instead.

## Page metadata

`pnpm run test:seo` gates CI on the built HTML, so a page with sloppy
frontmatter fails the build for everyone. When you create or rename a page:

- **`title`** — at most 36 characters. Starlight appends
  `" | Giskard Documentation"` (24 chars) and the check bounds the rendered
  `<title>` at 60.
- **`description`** — 120-158 characters. Below 120 Google pads the snippet with
  its own choice of page text; above 158 it truncates.
- Both must be **unique across the whole site**. Two pages sharing a title
  compete for the same query. Where a concept page and a product page cover the
  same subject, split them by intent: the glossary takes the concept framing
  ("What Is Prompt Injection?"), the product section takes the feature framing
  ("Prompt Injection Detection").
- Changing a `title` for any of the above also changes the sidebar. If the old
  wording was the better label, pin it with `sidebar.label` so navigation does
  not shift.
