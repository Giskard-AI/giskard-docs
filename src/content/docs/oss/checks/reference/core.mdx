## `Check`

**Module:** `giskard.checks.core.check`

Base class for all checks. Subclass and register with `@Check.register("kind")` to create custom validation logic.

<TypeTable name="Check">
  <Property name="name" type="str | None" defaultValue="None">
    Optional check name for reporting.
  </Property>
  <Property name="description" type="str | None" defaultValue="None">
    Human-readable description of what the check validates.
  </Property>
</TypeTable>

<MethodCard name="async .run()" returnType="CheckResult">
  Execute the check logic against the provided trace. `run` is `async def` on the base class and raises `NotImplementedError`; every subclass must override it with an `async def` of its own.

  <Property name="trace" type="Trace" required>The trace containing interaction history. Access the current interaction via `trace.last`.</Property>
</MethodCard>

**Raises:** `NotImplementedError` from the base implementation. `ValidationError` at construction on any unknown keyword argument, because `Check` sets `extra="forbid"` — see [Errors](#errors).

## `CheckResult`

**Module:** `giskard.checks.core.result`

Immutable result produced by running a check.

<TypeTable name="CheckResult">
  <Property name="status" type="CheckStatus">
    Outcome status (PASS, FAIL, ERROR, SKIP).
  </Property>
  <Property name="message" type="str | None">
    Optional short message to surface to users.
  </Property>
  <Property name="metrics" type="list[Metric]">
    List of auxiliary metrics captured by the check.
  </Property>
  <Property name="details" type="dict[str, Any]">
    Arbitrary structured payload with additional context.
  </Property>
</TypeTable>

### Factory methods

Four classmethods build a result. Every argument is **keyword-only**, so `CheckResult.success("ok")` raises `TypeError`:

```python
from giskard.checks import CheckResult, Metric

passed = CheckResult.success(
    message="All validations passed",
    details={"score": 0.95},
    metrics=[Metric(name="score", value=0.95)],
)
failed = CheckResult.failure(
    message="Score below threshold", details={"score": 0.65}
)
errored = CheckResult.error(message="Failed to connect to API")
skipped = CheckResult.skip(message="No outputs available")
```

`success()` and `failure()` accept `message`, `details`, and `metrics`. `error()` and `skip()` accept only `message` and `details` — a result that reached no verdict carries no measurement.

A `CheckResult` is a frozen Pydantic model, so its repr shows every field:

```text
CheckResult(status=<CheckStatus.FAIL: 'fail'>, message='Expected authenticated, got 1,284.50 EUR', metrics=[], details={'check_name': 'Equals'})
```

The runner writes `check_name` (and `check_kind`) into `details`, which is where the reports get the label they print beside each verdict.

### Instance properties

<Property name="passed" type="bool">
  True if status is PASS.
</Property>
<Property name="failed" type="bool">
  True if status is FAIL.
</Property>
<Property name="errored" type="bool">
  True if status is ERROR.
</Property>
<Property name="skipped" type="bool">
  True if status is SKIP.
</Property>

## `Metric`

**Module:** `giskard.checks.core.result`

Named quantitative measurement attached to a check result (e.g. performance timings, confidence scores).

<TypeTable name="Metric">
  <Property name="name" type="str" required>
    Identifier for the metric.
  </Property>
  <Property name="value" type="float" required>
    Numerical value of the metric.
  </Property>
</TypeTable>

Attach metrics to a result to record a number alongside the verdict. They travel with the `CheckResult`, so a suite can report _how close_ a check was, not just whether it passed:

```python
from giskard.checks import CheckResult, Metric

score = 0.82
return CheckResult.success(
    message=f"Retrieval score {score}",
    metrics=[Metric(name="retrieval_score", value=score)],
)
```

Only `success()` and `failure()` accept `metrics`.

## `CheckStatus`

**Module:** `giskard.checks.core.result`

Enumeration of possible check execution outcomes. It subclasses `str`, so a member compares equal to its **lowercase** value:

| Member  | Value     | Description                                   |
| ------- | --------- | --------------------------------------------- |
| `PASS`  | `"pass"`  | Check validation succeeded                    |
| `FAIL`  | `"fail"`  | Check validation failed                       |
| `ERROR` | `"error"` | Unexpected error during check execution       |
| `SKIP`  | `"skip"`  | Check was skipped (e.g. precondition not met) |

```python
from giskard.checks import CheckStatus

if result.status == CheckStatus.PASS:
    print("Success!")

result.status == "pass"  # True
result.status == "PASS"  # False — the value is lowercase
```

:::caution
Comparing against an uppercase string never matches and never raises, so a
`if result.status == "PASS"` branch silently becomes dead code. Compare against
the enum member, or against the lowercase value.
:::

`ScenarioStatus` and `TestCaseStatus` are separate enums with exactly the same four members and the same lowercase values. Use the one that matches the result object you are holding.

## `Interaction`

**Module:** `giskard.checks.core.interaction` (also exported from `giskard.checks`)

A single exchange between inputs and outputs.

<TypeTable name="Interaction">
  <Property name="inputs" type="InputType">
    Input values for this interaction (e.g. user message, API request).
  </Property>
  <Property name="outputs" type="OutputType">
    Output values produced in response (e.g. assistant reply, API response).
  </Property>
  <Property name="metadata" type="dict[str, Any]">
    Optional metadata (timing, tool calls, intermediate states, etc.).
  </Property>
</TypeTable>

```python
from giskard.checks import Interaction

# Plain text in, plain text out
interaction = Interaction(
    inputs="How long does a SEPA transfer take?",
    outputs="A SEPA transfer arrives within one working day and is free.",
    metadata={"model": "gpt-5", "tokens": 15},
)

# Structured, so checks can address individual fields
interaction = Interaction(
    inputs={"question": "What is my current balance?", "customer_id": "C-8841"},
    outputs={"intent": "balance_enquiry", "authenticated": True},
    metadata={"retrieval_score": 0.91, "latency_ms": 320},
)
```

:::note
Interactions are typically created through the scenario builder's `.interact()` method rather than directly instantiated.
:::

## `Trace`

**Module:** `giskard.checks.core.interaction` (also exported from `giskard.checks`)

Immutable history of all interactions in a scenario. Passed to checks for validation and to interaction specs for generating subsequent interactions.

<TypeTable name="Trace">
  <Property name="interactions" type="list[Interaction]">
    Ordered list of all interactions. Most recent at `[-1]`.
  </Property>
  <Property name="annotations" type="dict[str, Any]">
    Optional scenario-level metadata (for example tenant id or experiment name).
    Populated from `Scenario(..., annotations=...)` when the runner creates the
    initial trace.
  </Property>
  <Property name="last" type="Interaction | None">
    Computed property returning the last interaction, or None if empty.
  </Property>
</TypeTable>

```python
from giskard.checks import Check, CheckResult, Trace


# Access trace in checks
@Check.register("interaction_count")
class TraceCheck(Check):
    async def run(self, trace: Trace) -> CheckResult:
        last = trace.last  # most recent interaction
        all_interactions = trace.interactions  # full history
        count = len(trace.interactions)
        return CheckResult.success(message=f"Processed {count} interactions")
```

### Builder methods

`Trace` is frozen, so these return a **new** trace rather than mutating the one you called them on. All four are async, because a spec may have to call your agent to produce the interactions it appends.

<MethodCard name="async Trace.from_interactions()" returnType="Trace">
  Classmethod. Build a trace from scratch out of concrete interactions and/or interaction specs.

  <Property name="*interactions" type="Interaction | InteractionGenerator" required>Interactions to append and specs to generate from, in order.</Property>
</MethodCard>

<MethodCard name="async .with_interactions()" returnType="Trace">
  Return this trace extended with every given interaction or spec, in order.

  <Property name="*interactions" type="Interaction | InteractionGenerator" required>Interactions to append and specs to generate from.</Property>
</MethodCard>

<MethodCard name="async .with_interaction()" returnType="Trace">
  Return this trace extended with one interaction, or with every interaction a single spec generates.

  <Property name="interaction" type="Interaction | InteractionGenerator" required>The interaction or spec to append.</Property>
</MethodCard>

<MethodCard name="Trace.for_target()" returnType="Trace">
  Classmethod, and the only synchronous one. Build an empty trace whose type is inferred from a target's annotations, falling back to the plain class when nothing can be inferred.

  <Property name="target" type="Target" required>The system under test to infer the trace type from.</Property>
</MethodCard>

**Raises:** `InteractionGenerationError` from the three async methods when a spec fails partway through. The exception carries a `partial_trace` holding every interaction completed before the failure — including those appended by earlier calls in the same chain — and chains the original error as its `__cause__`.

```python
from giskard.checks import Interaction, InteractionGenerationError, Trace

try:
    trace = await Trace.from_interactions(
        Interaction(inputs="Hello", outputs="Hi"),
        flaky_spec,
    )
except InteractionGenerationError as exc:
    print(f"Got {len(exc.partial_trace.interactions)} interactions before failing")
    raise exc.__cause__ from None
```

### Custom trace types

Pass `trace_type=YourTrace` on [`Scenario`](/oss/checks/reference/scenarios) when you subclass `Trace` to add computed fields, helpers, or custom **Rich** rendering (`__rich_console__` / `__rich__`). The scenario runner constructs the initial trace with `YourTrace(annotations=scenario.annotations)`.

`ScenarioResult.final_trace` is validated as the base `Trace` type; after `run()`, rebuild your subclass from `final_trace.interactions` and `final_trace.annotations` if you need the custom Rich layout in a report. Checks still receive your subclass during execution. See [Custom trace types](/oss/checks/how-to/custom-trace).

### Rich rendering

The default `Trace.__rich_console__` prints each interaction under a titled rule. Override it on a subclass for conversation-style or domain-specific layouts. [`ScenarioResult.print_report()`](/oss/checks/reference/scenarios#scenarioresult) renders `final_trace` with Rich using that protocol when the stored trace implements it.

## `InteractionSpec`

**Module:** `giskard.checks.core.interaction`

Declarative specification for generating interactions. Supports static values or callables that compute values based on the current trace.

```python
from giskard.checks import Scenario


def target(inputs: str) -> str:
    return f"Received: {inputs}"


# Static values: a recorded exchange, no agent called
scenario = Scenario("recorded").interact(
    inputs="Hello",
    outputs="Received: Hello",
)

# Callable outputs: the agent runs
scenario = Scenario("live").interact(
    inputs="Hello",
    outputs=target,
)

# Callable inputs: the next message depends on the last reply.
# trace.last is None on the first interaction, so guard it.
scenario = (
    Scenario("follow_up")
    .interact(
        inputs="Hello",
        outputs=target,
    )
    .interact(
        inputs=lambda trace: f"Repeat: {trace.last.outputs}",
        outputs=target,
    )
)
```

## `Interact`

**Module:** `giskard.checks.core.interaction`

The concrete `InteractionSpec` that `.interact()` builds. Construct it directly when you want to hold a spec as a value — to reuse it across scenarios, to pass it to [`WithSpy`](/oss/checks/reference/testing-utils#withspy), or to fill in the outputs later.

<TypeTable name="Interact">
  <Property name="inputs" type="InputGenerator | value | Callable" required>
    A static value, a callable, a generator, or an `InputGenerator`. A callable
    may declare a `trace` parameter and nothing else required.
  </Property>
  <Property name="outputs" type="Target | MISSING" defaultValue="MISSING">
    A static value or a callable `(inputs)` / `(inputs, trace)`. Left at
    `MISSING`, the interaction uses the scenario-level or run-level target; if
    there is none, generation raises `ValueError`.
  </Property>
  <Property name="metadata" type="dict[str, Any]" defaultValue="{}">
    Metadata copied onto every interaction this spec produces.
  </Property>
</TypeTable>

<MethodCard name=".set_outputs()" returnType="Interact">
  Set the outputs after construction and revalidate the injection mapping. Returns self for chaining.

  <Property name="outputs" type="Target | MISSING" required>The new outputs specification.</Property>
</MethodCard>

<MethodCard name="async .generate()" returnType="AsyncGenerator[Interaction, Trace]">
  Drive the spec: resolve inputs, call the target, and yield one `Interaction` at a time, receiving the updated trace back through `asend()` between yields. The scenario runner calls this for you.

  <Property name="trace" type="Trace" required>The trace as it stands before this spec runs.</Property>
</MethodCard>

```python
from giskard.checks import Interact, Scenario

spec = Interact(inputs="Find item 42")
spec.set_outputs(my_agent)

scenario = Scenario("reusable").add_interaction(spec)
```

**Raises:** `ValueError` at construction when a callable declares a required parameter that cannot be injected — `outputs` may take `inputs` and `trace`, `inputs` may take `trace` and `input_type`, and any other required name is rejected. `ValueError` during generation when `outputs` is `MISSING` and no target was bound.

## `Target`

**Module:** `giskard.checks.core.types` (also exported from `giskard.checks`)

The type of every `target=` and `outputs=` parameter in the API. A target is your system under test, expressed as one of:

- a plain value, used as-is;
- a callable `(inputs) -> outputs`;
- a callable `(inputs, trace) -> outputs`;
- either callable declared `async`.

The parameter **names** are what the framework dispatches on, not their positions. Name them `inputs` and `trace`; any other required parameter name raises `TypeError: Parameter '<name>' is required but not in the injection requirements`.

```python
from giskard.checks import Scenario, Target


async def my_agent(inputs: str) -> str:
    return f"Received: {inputs}"


target: Target = my_agent

scenario = Scenario("uses_target").with_target(target).interact(inputs="Hello")
```

## Mixins

**Module:** `giskard.checks.core.mixin`

Two mixins give a custom check the same model-configuration field the built-ins have, including the fallback to the global default. Both are exported from `giskard.checks` for exactly this purpose.

<TypeTable name="WithGeneratorMixin">
  <Property name="generator" type="BaseGenerator | None" defaultValue="None">
    LLM generator for this check. `None` falls back to
    `get_default_generator()`. Read it inside `run()` as `self._generator`,
    which resolves the fallback.
  </Property>
</TypeTable>

<TypeTable name="WithEmbeddingMixin">
  <Property
    name="embedding_model"
    type="BaseEmbeddingModel | None"
    defaultValue="None"
  >
    Embedding model for this check. `None` falls back to
    `get_default_embedding_model()`. Read it as `self._embedding_model`.
  </Property>
</TypeTable>

```python
from giskard.checks import Check, CheckResult, Trace, WithGeneratorMixin


@Check.register("asks_the_model")
class AsksTheModel(Check, WithGeneratorMixin):
    async def run(self, trace: Trace) -> CheckResult:
        generator = self._generator  # explicit one, or the global default
        ...
```

## Exceptions

**Module:** `giskard.checks.core.exceptions`

<TypeTable name="InteractionGenerationError">
  <Property name="partial_trace" type="Trace">
    Trace containing every interaction completed before the failure. This is the
    only way to see how far a scenario got. The error that stopped the generator
    is chained as `__cause__`.
  </Property>
</TypeTable>

Raised out of `Trace.with_interaction()` and its siblings. `Scenario.run()` unwraps it and re-raises the underlying cause unless you pass `return_exception=True`, in which case the step comes back as a `TestCaseResult` with an `error` and its checks marked SKIP.

`InputGenerationException` is raised by `BaseLLMGenerator` when a turn cannot be produced after `max_retries + 1` attempts — because the model refused, the provider blocked the request, or the output did not fit the input schema.

`TestCaseError` is not an exception you catch. It is the frozen model attached to `TestCaseResult.error` recording why a step could not run:

<TypeTable name="TestCaseError">
  <Property name="message" type="str" required>
    The `str()` of the original exception.
  </Property>
  <Property name="exception_type" type="str" required>
    Its class name.
  </Property>
  <Property name="traceback" type="str | None" defaultValue="None">
    Formatted traceback, when one was captured.
  </Property>
  <Property name="phase" type="str | None" defaultValue="None">
    Where it happened, for example `"input_generation"`.
  </Property>
</TypeTable>

Call `.summary()` for the one-line form, `<ExceptionType> during <phase>: <message>`.

## Errors

The errors you are most likely to meet, and what each one means.

| Error                                                                             | Cause                                                                                           | Fix                                                          |
| --------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| `ValidationError: … extra_forbidden` on a check                                   | `Check` sets `extra="forbid"`, so a misspelled or renamed field is rejected rather than dropped | Check the field name against this reference                  |
| A `Scenario(...)` keyword that silently does nothing                              | `Scenario` deliberately does **not** forbid extras (see below)                                  | Put scenario metadata in `annotations`, not at the top level |
| `ValidationError: Invalid JSONPath expression '…': path must start with 'trace.'` | Any `*_key` field is a `JSONPathStr`                                                            | Prefix the path with `trace.`                                |
| `CheckResult.error` mentioning "No value found for key"                           | The path resolved to `NoMatch` — a typo, or the output shape changed                            | Print `trace.last.outputs` and correct the path              |
| `TypeError: Parameter 'x' is required but not in the injection requirements`      | A callable declared a parameter the framework cannot supply                                     | Name it `inputs` or `trace`, or give it a default            |
| `InteractionGenerationError` out of `Scenario.run()`                              | A spec failed mid-scenario                                                                      | Read `.partial_trace`, or pass `return_exception=True`       |
| `TypeError: from_fn callable must return bool or CheckResult`                     | An `FnCheck` function returned something else                                                   | Return a `bool` or a `CheckResult`                           |
| `TypeError` / `ValueError` from `Suite.run()`                                     | `max_concurrency` is not a positive integer — validated even when `parallel=False`              | Pass a positive `int`, or `None`                             |

### The `extra="forbid"` asymmetry

`Check` forbids unknown fields; `Scenario` and `Suite` accept them. This is deliberate rather than an oversight, and it catches people out, so it is worth stating plainly.

A check is written by you, so a misspelled field is a bug and failing loudly is right: without `extra="forbid"`, a persisted suite referring to a renamed field would fall back to that field's default and run **green while evaluating the wrong value**.

A scenario may instead be parsed from JSONL hosted in a remote dataset repository that releases on its own schedule. Forbidding extras there would turn any field added upstream into an instant hard failure for every installed version. The cost is that unknown scenario keys are dropped without a word — so metadata that has to survive parsing belongs in `annotations`, which is a real field.

`Step` follows `Check` and forbids extras: both of its fields default to an empty list, so a misspelled key would otherwise yield a step that runs its interactions and asserts nothing.

## `Scenario`

**Module:** `giskard.checks.core.scenario`

An ordered sequence of steps — interaction specs followed by checks — executed against one shared trace.

[**Scenarios**](/oss/checks/reference/scenarios) is the canonical page for `Scenario`: the constructor fields, all ten builder methods, `.run()`, and `ScenarioResult`. It is documented there rather than here so the two pages cannot drift apart.

```python
from giskard.checks import Equals, Scenario

result = await (
    Scenario("two_step_example")
    .interact(inputs="Find item 42", outputs=my_agent)
    .check(Equals(expected_value="found", target_key="trace.last.outputs.status"))
    .run()
)
```

## `Step`

**Module:** `giskard.checks.core.scenario`

A scenario step: a sequence of interaction specs followed by checks. Each step maps to one test case at runtime.

<TypeTable name="Step">
  <Property name="interacts" type="list[InteractionSpec]">
    Interaction specs to apply to the trace in this step.
  </Property>
  <Property name="checks" type="list[Check]">
    Checks to run against the trace after interactions in this step.
  </Property>
</TypeTable>

```python
from giskard.checks import Scenario, Step, Interact, StringMatching

scenario = Scenario(
    name="greeting",
    steps=[
        Step(
            interacts=[
                Interact(
                    inputs="Hello",
                    outputs="How can I help?",
                )
            ],
            checks=[
                StringMatching(keyword="?", target_key="trace.last.outputs")
            ],
        ),
    ],
)
```

## `Extractors`

**Module:** `giskard.checks.core.extraction`

### `resolve()`

Extract values using JSONPath expressions from a trace.

<MethodCard name="resolve()" returnType="Any | list[Any] | NoMatch">
  Evaluate a JSONPath expression against `trace.model_dump()` and return what it matches.

  <Property name="trace" type="Trace" required>
    The trace to extract from. It is dumped to plain dicts first, so `resolve`
    never sees your Pydantic instances — only their serialized form.
  </Property>
  <Property name="key" type="str" required>
    JSONPath expression to evaluate against the trace.
  </Property>
</MethodCard>

**Returns:** a single value for a single match; a **list** of every match when the expression matches more than once or is inherently a list expression (a wildcard, slice, union, or descendant path); a `NoMatch` sentinel when nothing matched. See [Multi-match paths](/oss/checks/explanation/jsonpath-in-checks#multi-match-paths).

`resolve` does **not** require the `trace.` prefix — that rule belongs to the `JSONPathStr` field validator on the checks. Calling `resolve(trace, "last.outputs")` yourself just returns `NoMatch`.

```python
from giskard.checks import Interaction, Trace, resolve
from giskard.checks.core.extraction import NoMatch

trace = Trace(
    interactions=[
        Interaction(
            inputs="What is the monthly fee on my current account?",
            outputs={"intent": "fee_enquiry", "fee_eur": 3.00},
            metadata={"model": "gpt-5"},
        )
    ]
)

intent = resolve(trace, "trace.last.outputs.intent")  # "fee_enquiry"

missing = resolve(trace, "trace.last.outputs.account_number")
if isinstance(missing, NoMatch):
    pass  # the field is absent; comparison checks report ERROR, not FAIL

model_name = resolve(trace, "trace.interactions[0].metadata.model")
```

**Common JSONPath patterns:**

| Pattern                   | Description                             |
| ------------------------- | --------------------------------------- |
| `trace.last.inputs`       | Last interaction inputs                 |
| `trace.last.outputs`      | Last interaction outputs                |
| `trace.last.metadata.key` | Metadata from last interaction          |
| `trace.interactions[0]`   | First interaction                       |
| `trace.interactions[-1]`  | Last interaction (same as `trace.last`) |

## Configuration

**Module:** `giskard.checks`

`set_default_generator()` and `get_default_generator()` set and read the process-wide LLM used by every judge constructed without an explicit `generator`. They are documented, together with the environment variables behind them and the rule that a runtime override wins over `GISKARD_CHECKS_DEFAULT_MODEL`, on [Settings](/oss/checks/reference/settings#default-generator).

```python
from giskard.agents.generators import Generator
from giskard.checks import Groundedness, set_default_generator

set_default_generator(Generator(model="openai/gpt-4o-mini"))

check = Groundedness()  # uses the default generator
```
