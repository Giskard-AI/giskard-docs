## `Scenario`

**Module:** `giskard.checks.core.scenario`

This is the canonical page for `Scenario`. Create one, add interactions and checks, then call `.run()`. Every builder method returns the same scenario, so they chain.

A scenario is a list of **steps**. A step is a group of interaction specs followed by the checks that validate them. `.interact()` appends to the current step, or opens a new one if the current step already has checks; `.check()` adds to the current step. Steps run in order against a shared trace and execution stops at the first step that does not pass — see [Core concepts](/oss/checks/explanation/core-concepts).

### Constructor

<MethodCard name="Scenario()" returnType="Scenario">
  Create a new scenario. Every field is also settable after construction, most of them through a `with_*` method.

  <Property name="name" type="str" defaultValue='"Unnamed Scenario"'>Scenario name for identification. Pass the first argument positionally as in <code>Scenario("my_name")</code>.</Property>
  <Property name="steps" type="list[Step]" defaultValue="[]">Pre-built steps. The fluent methods append to this list for you; pass it directly only when you are constructing a scenario programmatically.</Property>
  <Property name="trace_type" type="type[TraceType] | None" defaultValue="None">Custom `Trace` subclass to use. Inferred from the components when `None`.</Property>
  <Property name="annotations" type="dict[str, Any]" defaultValue="{}">Key-value pairs merged into the trace at run start and readable as `trace.annotations`.</Property>
  <Property name="target" type="Target | MISSING" defaultValue="MISSING">Default system under test, used for every interaction whose `outputs` is `MISSING`.</Property>
  <Property name="multiple_runs" type="int" defaultValue="1">Default cap on full scenario executions when <code>run()</code> is called without <code>multiple_runs=...</code>. Must be ≥ 1.</Property>
  <Property name="tags" type="list[str]" defaultValue="[]">Flat `"Key:Value"` labels used for grouping results and for Hub upload. A tag without a `:` is a bare boolean label.</Property>
</MethodCard>

:::note[Unknown fields are accepted, then dropped]
Unlike `Check`, `Scenario` does not set `extra="forbid"`, so a misspelled constructor keyword raises nothing and is silently discarded. Scenario metadata that has to survive belongs in `annotations`. See [Errors](/oss/checks/reference/core#errors) for why the two classes differ.
:::

  <Property name="interaction" type="InteractionSpec" required>The interaction spec to add.</Property>
</MethodCard>

<MethodCard name=".add_interactions()" returnType="self">
  Add several pre-constructed interaction specs to the same step.

  <Property name="*interactions" type="InteractionSpec" required>The interaction specs to add, in order.</Property>
</MethodCard>

<MethodCard name=".append()" returnType="self">
  Add one component of either kind. Dispatches to `.check()` for a `Check` and to `.add_interaction()` for an interaction spec, which is useful when you are iterating over a mixed list.

  <Property name="component" type="InteractionSpec | Check" required>The component to append.</Property>
</MethodCard>

<MethodCard name=".extend()" returnType="self">
  Append one or more interaction specs and/or checks, in order. Calls `.append()` for each.

  <Property name="*components" type="InteractionSpec | Check" required>Components to append in order.</Property>
</MethodCard>

<MethodCard name=".with_target()" returnType="self">
  Set the default system under test. Every interaction whose `outputs` is `MISSING` calls it. This is how you bind an agent once instead of repeating `outputs=` on each `.interact()`.

  <Property name="target" type="Target" required>Callable producing outputs from inputs, and optionally the trace. See [`Target`](/oss/checks/reference/core#target).</Property>
</MethodCard>

<MethodCard name=".with_annotations()" returnType="self">
  Replace the scenario's annotations. They are merged into the trace at run start and are readable as `trace.annotations` from checks and callables, so shared context does not have to be attached to every interaction.

  <Property name="annotations" type="dict[str, Any]" required>Key-value pairs to expose on the trace.</Property>
</MethodCard>

<MethodCard name=".with_tags()" returnType="self">
  Replace the scenario's tags. Tags are flat `"Key:Value"` strings; a tag without a `:` is a bare label. They are copied onto `ScenarioResult.tags` and are what [`SuiteResult.group_by()`](#grouping-results-by-tag) slices on.

  <Property name="tags" type="list[str]" required>The tags to set.</Property>
</MethodCard>

<MethodCard name="async .run()" returnType="ScenarioResult">
  Execute the scenario against the SUT and return results.

  <Property name="target" type="Target | MISSING" defaultValue="MISSING">Override the scenario's default target for this run. Left at `MISSING`, the scenario's own `target` is used.</Property>
  <Property name="return_exception" type="bool" defaultValue="False">If True, exceptions become `CheckResult.error` entries and a `TestCaseError` on the step instead of propagating.</Property>
  <Property name="multiple_runs" type="int | None" defaultValue="None">When set, overrides the scenario’s `multiple_runs` field: maximum full scenario executions (fresh trace each time). Each run must pass for the next to run; stops on the first FAIL, ERROR, or SKIP. Not a retry-until-success loop.</Property>
</MethodCard>

**Raises:** `InteractionGenerationError`'s underlying cause when a spec fails partway through and `return_exception` is `False`. Pass `return_exception=True` to get a result back instead, or catch it and read [`.partial_trace`](/oss/checks/reference/core#exceptions).

### Binding a target

`outputs` on an interaction is optional **only** when a target is bound, either on the scenario, on the suite, or on the `run()` call. Without one, generation raises `ValueError: Interaction outputs are not provided and no target was bound.`

```python
from giskard.checks import Scenario, StringMatching


async def my_agent(inputs: str) -> str:
    return f"Received: {inputs}"


async def my_other_agent(inputs: str) -> str:
    return f"Received (v2): {inputs}"


scenario = (
    Scenario("bound_target")
    .with_target(my_agent)
    .with_tags(["Category:Smoke", "Owner:platform"])
    .interact(inputs="Hello")  # no outputs= needed
    .checks(
        StringMatching(keyword="Received", target_key="trace.last.outputs"),
        StringMatching(keyword="Hello", target_key="trace.last.outputs"),
    )
)

result = await scenario.run()
result = await scenario.run(target=my_other_agent)  # compare two implementations
```

### Repeating a scenario

`multiple_runs` re-runs the whole scenario with a fresh trace each time, which is the built-in answer to a flaky agent or a flaky judge:

```python
result = await scenario.run(multiple_runs=5)
print(f"{result.runs_executed} of {result.multiple_runs} runs executed")
```

Every run must pass for the next to start, and execution stops on the first run that comes back FAIL, ERROR, or SKIP. It raises the bar rather than lowering it — this is **not** a retry-until-one-success mode. The returned `ScenarioResult` describes the last run executed.

### Multi-step example

Each step can add interactions and then validate the trace:

```python
from giskard.checks import Scenario, FnCheck, Equals

result = await (
    Scenario("two_step_example")
    .interact(
        inputs="Find item 42",
        outputs={"answer": "Which collection?", "found": False},
    )
    .check(
        FnCheck(
            fn=lambda trace: trace.last is not None
            and "?" in trace.last.outputs["answer"],
            name="asks_follow_up",
        )
    )
    .interact(
        inputs="In the archive",
        outputs={"answer": "Item found", "found": True},
    )
    .check(Equals(expected_value=True, target_key="trace.last.outputs.found"))
    .run()
)
```

### Dynamic interactions

Pass a callable as `outputs` to run the agent instead of replaying a recorded reply:

```python
from giskard.checks import Scenario


def bank_support_agent(inputs: str) -> str:
    """Stand-in for the agent under test. Replace with your own call."""
    if "transfer" in inputs.lower():
        return "A SEPA transfer arrives within one working day and is free."
    return "Could you tell me a bit more about what you need?"


scenario = Scenario("transfer_timing").interact(
    inputs="How long does a SEPA transfer take?", outputs=bank_support_agent
)
```

### Context-aware interactions

Pass a callable as `inputs` when the next message depends on what the agent said:

```python
scenario = (
    Scenario("bank_agent_follow_up")
    .interact(
        inputs="How long does a SEPA transfer take?",
        outputs=bank_support_agent,
    )
    .interact(
        inputs=lambda trace: f"You said: {trace.last.outputs} Is that the same at a weekend?",
        outputs=bank_support_agent,
    )
)
```

## `ScenarioResult`

**Module:** `giskard.checks.core.result`

Result of scenario execution with trace and check results.

<TypeTable name="ScenarioResult">
  <Property name="scenario_name" type="str">
    Name of the scenario that produced this result.
  </Property>
  <Property name="status" type="ScenarioStatus">
    Overall status (PASS/FAIL/ERROR/SKIP).
  </Property>
  <Property name="steps" type="list[TestCaseResult]">
    Results for each step (interactions in that step, then checks).
  </Property>
  <Property name="final_trace" type="Trace">
    Complete trace of all interactions.
  </Property>
  <Property name="passed" type="bool">
    True when the aggregated status is PASS (no failures or errors; not the
    all-skipped case).
  </Property>
  <Property name="failed" type="bool">
    True when at least one step failed and none errored.
  </Property>
  <Property name="errored" type="bool">
    True when at least one step errored.
  </Property>
  <Property name="skipped" type="bool">
    True when all steps were skipped.
  </Property>
  <Property name="duration_ms" type="int">
    Total execution time in milliseconds.
  </Property>
  <Property name="multiple_runs" type="int">
    Configured cap on full scenario executions for this invocation (from the
    scenario or the `run(multiple_runs=...)` override).
  </Property>
  <Property name="runs_executed" type="int">
    How many full scenario executions ran before stopping (at most
    `multiple_runs`).
  </Property>
  <Property name="tags" type="list[str]">
    Snapshot of the scenario's tags at run time. `SuiteResult.group_by()` reads
    these.
  </Property>
  <Property name="failures_and_errors" type="list[TestCaseResult]">
    The steps that failed or errored. Skipped steps are excluded, so this is the
    list to iterate in CI. Property, not a field.
  </Property>
</TypeTable>

`status` is derived from the steps, in priority order: ERROR if any step errored, FAIL if any failed, SKIP if all were skipped, PASS otherwise. A scenario with **no steps at all** is PASS.

<MethodCard name=".print_report()" returnType="None">
  Print the result to the terminal with Rich, including the trace and every check verdict. Inherited from `BaseResult`, so `CheckResult`, `TestCaseResult`, and `SuiteResult` all have it.

  <Property name="console" type="Console | None" defaultValue="None">Rich `Console` to print to. Defaults to a new one writing to stdout.</Property>
</MethodCard>

### What a report looks like

A two-step scenario where the first step fails. `print_report()` writes this to the terminal, in colour:

```text
─────────────────────────────── ❌ FAILED ────────────────────────────────
mentions_currency       PASS
cites_account   FAIL    The answer does not contain the keyword 'account
ending'
mentions_savings        SKIP
───────────────────────────────── Trace ──────────────────────────────────
───────────────────────────── Interaction 1 ──────────────────────────────
Inputs: 'What is my balance?'
Outputs: 'Your balance is 1,284.50 EUR.'
─────────────────────── 2 steps in 4ms | runs: 1/1 ───────────────────────
```

Three things to read out of it. Each row is one check: its `name`, its status, and the reason a non-passing check gives. `mentions_savings` is SKIP rather than FAIL because it belongs to the second step, and the first step failed — the second interaction never ran, which is also why the trace shows one interaction and not two. The footer counts steps, not checks, and reports how many full runs executed.

Reading the same result in code:

```python
result = await scenario.run()
result.print_report()

failures = [
    message
    for step in result.failures_and_errors
    for message in step.format_failures()
]
print(failures)
# ["cites_account FAILED: The answer does not contain the keyword 'account ending'"]

assert result.passed, failures
```

`failures_and_errors` is a `list[TestCaseResult]` (one per non-passing step) and `format_failures()` returns one readable string per failing check, so the assertion message names exactly what went wrong.

## `Suite`

**Module:** `giskard.checks.scenarios.suite`

Group multiple scenarios and run them together.

<MethodCard name="Suite()" returnType="Suite">
  <Property name="name" type="str" required>
    Suite identifier.
  </Property>
  <Property name="scenarios" type="list[Scenario]" defaultValue="[]">
    Scenarios in the suite. Pass them here to build a suite in one expression,
    or add them afterwards with `.append()`.
  </Property>
  <Property name="target" type="Target | MISSING" defaultValue="MISSING">
    Suite-level target SUT. It overrides any scenario-level target.
  </Property>
</MethodCard>

<MethodCard name=".append()" returnType="Suite">
  Add a scenario to the suite.

  <Property name="scenario" type="Scenario" required>The scenario to add.</Property>
</MethodCard>

<MethodCard name="async .run()" returnType="SuiteResult">
  Run every scenario in the suite.

  <Property name="target" type="Target | MISSING" defaultValue="MISSING">Override target for this run. Overrides both the suite-level target and any scenario-level target.</Property>
  <Property name="return_exception" type="bool" defaultValue="False">Return results on exceptions.</Property>
  <Property name="parallel" type="bool" defaultValue="False">Run scenarios concurrently while preserving result order. The scan helpers pass `parallel=True`; `Suite.run` on its own is serial.</Property>
  <Property name="max_concurrency" type="int | None" defaultValue="None">Cap on concurrent scenarios when `parallel=True`. `None` starts them all at once, so your provider's rate limit becomes the real cap.</Property>
  <Property name="verbose" type="bool" defaultValue="True">Show a progress bar naming the running scenario. Set to `False` in CI.</Property>
</MethodCard>

**Raises:** `TypeError` when `max_concurrency` is neither `None` nor an `int` (a `bool` is rejected too), and `ValueError` when it is below 1. Both are validated before anything runs, and **even when `parallel=False`**, where the value has no effect on scheduling.

Set the target once on the suite and leave `outputs` off each interaction:

```python
from giskard.checks import Scenario, StringMatching, Suite


def target(inputs: str) -> str:
    return f"Received: {inputs}"


suite = Suite(name="examples", target=target)
suite.append(
    Scenario("contains_received").interact(
        inputs="Hello"
    ).check(
        StringMatching(
            keyword="Received", target_key="trace.last.outputs"
        )
    )
)
suite.append(
    Scenario("another_input").interact(inputs="Goodbye")
)

result = await suite.run()

rate = result.pass_rate
print("no scenarios evaluated" if rate is None else f"{rate:.0%}")
```

`pass_rate` is the fraction of non-skipped scenarios that passed.

```python
result.print_report(group_by="Category")

for name, stats in result.group_by("Category").groups.items():
    print(name, stats.pass_rate, stats.total)
```

### Grouping results by tag

`group_by()` slices a run by one tag key. A scenario carrying several tags with the same key lands in **each** matching bucket — a scenario testing two vulnerabilities affects both pass rates — so the bucket totals can add up to more than the number of scenarios. Scenarios with no tag for that key go into a `None` bucket, rendered as `(untagged)`.

  <Property name="key" type="str">
    The tag key that was grouped on.
  </Property>
  <Property name="groups" type="dict[str | None, GroupStats]">
    One entry per tag value, plus `None` for untagged scenarios.
  </Property>
</TypeTable>

<TypeTable name="GroupStats">
  <Property name="name" type="str | None">
    The tag value for this bucket, or `None` for untagged.
  </Property>
  <Property name="passed" type="int">
    Scenarios in this bucket that passed.
  </Property>
  <Property name="failed" type="int">
    Scenarios that failed.
  </Property>
  <Property name="errored" type="int">
    Scenarios that errored.
  </Property>
  <Property name="skipped" type="int">
    Scenarios that were skipped.
  </Property>
  <Property name="total" type="int">
    All four counts added together.
  </Property>

## `ScenarioRunner`

**Module:** `giskard.checks.scenarios.runner`

<MethodCard name="async .run()" returnType="ScenarioResult">

    The scenario to execute.
  </Property>
  <Property name="target" type="Target | MISSING" defaultValue="MISSING">

  </Property>
  <Property name="return_exception" type="bool" defaultValue="False">
    Return results on exceptions.
  </Property>
  <Property name="multiple_runs" type="int | None" defaultValue="None">
