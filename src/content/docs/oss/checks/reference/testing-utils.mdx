## `TestCase`

**Module:** `giskard.checks.core.testcase`

Bundle a trace with a set of checks to execute. Useful for testing against fixed interaction sequences or replaying recorded conversations.

:::note
For most use cases, use the `Scenario()` fluent API instead. `TestCase` is for advanced use cases where you need direct control over trace construction.
:::

<TypeTable name="TestCase">
  <Property name="name" type="str | None">
    Optional label for the test case.
  </Property>
  <Property name="trace" type="Trace" required>
    The trace containing interactions to test against.
  </Property>
  <Property name="checks" type="Sequence[Check]" required>
    Sequence of checks to run against the trace.
  </Property>
</TypeTable>

<MethodCard name="async .run()" returnType="TestCaseResult">
  Execute all checks against the trace.

  <Property name="return_exception" type="bool" defaultValue="False">If True, return results even when exceptions occur instead of raising.</Property>
</MethodCard>

<MethodCard name=".assert_passed()" returnType="None">
  Run the test case and assert that all checks passed. Raises `AssertionError`
  with formatted failure messages if any check fails.
</MethodCard>

A conversation you captured in production, replayed against checks without calling the agent again:

```python
from giskard.checks import TestCase, Trace, Interaction, Equals

trace = Trace(
    interactions=[
        Interaction(
            inputs="What is the monthly fee on my current account?",
            outputs={"intent": "fee_enquiry", "fee_eur": 3.00},
        ),
        Interaction(
            inputs="And to replace a lost card?",
            outputs={"intent": "fee_enquiry", "fee_eur": 0.00},
        ),
    ]
)

test_case = TestCase(
    name="fee_enquiry_replay",
    trace=trace,
    checks=[
        Equals(
            expected_value=3.00,
            target_key="trace.interactions[0].outputs.fee_eur",
        ),
        Equals(
            expected_value=0.00,
            target_key="trace.interactions[1].outputs.fee_eur",
        ),
    ],
)

result = await test_case.run()
```

### Integration with pytest

`assert_passed()` raises `AssertionError` with the check messages, so a failing check reads like any other pytest failure:

```python
import pytest

from giskard.checks import FnCheck, Interaction, TestCase, Trace


@pytest.mark.asyncio
async def test_vague_question_gets_a_follow_up():
    trace = Trace(
        interactions=[
            Interaction(
                inputs="Something is wrong with my account.",
                outputs="Sorry to hear that. Is it a payment, a card, or the balance?",
            )
        ]
    )
    test_case = TestCase(
        name="asks_a_follow_up",
        trace=trace,
        checks=[
            FnCheck(
                fn=lambda t: t.last is not None and "?" in t.last.outputs,
                name="asks_a_follow_up",
            ),
        ],
    )
    await test_case.assert_passed()
```

## `TestCaseResult`

**Module:** `giskard.checks.core.result`

Result of test case execution with check outcomes.

One `TestCaseResult` is produced per **step** of a scenario, which is why `ScenarioResult.steps` is a list of them.

<TypeTable name="TestCaseResult">
  <Property name="results" type="list[CheckResult]">
    Results from all checks, in the order they ran.
  </Property>
  <Property name="duration_ms" type="int">
    Execution time in milliseconds.
  </Property>
  <Property name="last_interaction_index" type="int | None" defaultValue="None">
    0-based index, in the scenario's final trace, of the last interaction this
    step added before its checks ran. `None` when the step added none. This is
    how a check verdict is attributed back to a specific turn.
  </Property>
  <Property name="error" type="TestCaseError | None" defaultValue="None">
    Why the step could not run at all — an input-generation failure, for
    example. See [`TestCaseError`](/oss/checks/reference/core#exceptions).
  </Property>
  <Property name="status" type="TestCaseStatus">
    Aggregated outcome. ERROR whenever `error` is set, then ERROR if any check
    errored, FAIL if any failed, SKIP if all were skipped, PASS otherwise.
  </Property>
  <Property name="passed" type="bool">
    True when every check passed — **and also when there are no checks at all**.
  </Property>
  <Property name="failed" type="bool">
    True when at least one check failed and none errored.
  </Property>
  <Property name="errored" type="bool">
    True when the step errored or any check errored.
  </Property>
  <Property name="skipped" type="bool">
    True when all checks were skipped.
  </Property>
  <Property name="failures_and_errors" type="list[CheckResult]">
    The check results that failed or errored. Excludes SKIP.
  </Property>
</TypeTable>

:::caution[A step with no checks passes]
`passed` is True when `results` is empty. A scenario built with `.interact()` and no `.check()` therefore reports PASS while asserting nothing, and looks identical in a report to one that genuinely passed. If a suite goes green unexpectedly, count the checks first.
:::

<MethodCard name=".format_failures()" returnType="list[str]">
  Render every non-passing check as `<check name> <STATUS>: <reason>`. Includes SKIP as well as FAIL and ERROR, and prepends `Test case ERRORED: …` when `error` is set — a step that did not pass should never be left unexplained. This is the diagnostic superset that `assert_passed()` uses.
</MethodCard>

<MethodCard name=".assert_passed()" returnType="None">
  Raise `AssertionError` carrying `format_failures()` if the test case did not pass. Useful in pytest.
</MethodCard>

<MethodCard name=".print_report()" returnType="None">
  Print the step to the terminal with Rich: one row per check, then a status-count footer.

  <Property name="console" type="Console | None" defaultValue="None">Rich `Console` to print to.</Property>
</MethodCard>

```python
result = await test_case.run()

if result.passed:
    print("All checks passed!")
else:
    for message in result.format_failures():
        print(message)
    # is_authenticated ERRORED: No value found for key
    # 'trace.last.metadata.authenticated', expected a value equal to True.

result.assert_passed()  # raises AssertionError with those same messages
```

`TestCaseStatus` is a `str` enum whose values are lowercase — `"pass"`, `"fail"`, `"error"`, `"skip"` — so `result.status == "PASS"` is always False. See [`CheckStatus`](/oss/checks/reference/core#checkstatus).

## `TestCaseRunner`

**Module:** `giskard.checks.testing.runner`

Low-level runner for executing test cases. Most users should use `test_case.run()` instead.

<MethodCard name=".run()" returnType="TestCaseResult">
  Execute a test case's checks against its trace.

  <Property name="test_case" type="TestCase" required>The test case to execute.</Property>
  <Property name="return_exception" type="bool" defaultValue="False">Return results on exceptions.</Property>
</MethodCard>

<MethodCard name="get_runner()" returnType="TestCaseRunner">
  Get the default process-wide singleton runner instance. `TestCase.run()` calls this for you.
</MethodCard>

```python
from giskard.checks.testing.runner import get_runner

result = await get_runner().run(test_case)
```

## `WithSpy`

**Module:** `giskard.checks.testing.spy`

Replace a function with a `MagicMock` while the wrapped interaction spec runs, then record what it was called with. Use it to assert that your agent passed the right arguments to an internal call.

<TypeTable name="WithSpy">
  <Property name="interaction_generator" type="InteractionSpec" required>
    The interaction spec to spy on.
  </Property>
  <Property name="target" type="str" required>
    Python import path of the function to patch, exactly as you would pass it to `unittest.mock.patch` (for example `"myapp.db.fetch_orders"`). This is not a JSONPath -- a trace expression such as `"trace.last.outputs"` raises.
  </Property>
</TypeTable>

After each interaction, the mock's call history is written to `Interaction.metadata` under the `target` string, then the mock is reset. The recorded keys are `call_count`, `call_args`, `call_args_list`, and `mock_calls`.

Assert that the target called a dependency:

{/* pyright-skip: This integration example imports the reader's application module. */}
```python
from giskard.checks import Scenario, Interact, WithSpy

from myapp.agent import answer

interaction_spec = Interact(
    inputs="Find item 42",
    outputs=answer,
)

spied_spec = WithSpy(
    interaction_generator=interaction_spec,
    target="myapp.db.fetch_item",  # Python import path, same as mock.patch
)

result = await Scenario("dependency_call").add_interaction(spied_spec).run()

# Spy data is keyed by the same import path
spy_data = result.final_trace.last.metadata.get("myapp.db.fetch_item")
print(spy_data["call_count"], spy_data["call_args"])
```

:::note[It serializes]
`WithSpy` is registered as the `InteractionSpec` kind `"with_spy"`, so a suite containing one round-trips through `model_dump()` and back. That is unlike [`FnCheck`](/oss/checks/reference/checks#fncheck), whose callable is excluded from serialization.
:::
