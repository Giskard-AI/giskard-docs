A generated suite is data. Serialise it once and every later run is a replay: same questions, same judges, no generation calls, and a pass rate you can actually compare against last week's. This guide covers the round trip and the things that bite — deserialisation, diffs, and when to regenerate.

[Run the Scan in CI](/oss/solutions/how-to/scan-in-ci) shows the pipeline this feeds; here we deal with the file itself.

## Generate once, write JSON

`generate_suite` stops after generation, which is what you want when the goal is the artifact rather than a report:

```python
import asyncio
from pathlib import Path

from giskard.scan import generate_suite, vulnerability_suite_generator_registry


async def main():
    suite = await generate_suite(
        description="A support agent for an online coffee shop.",
        languages=["en"],
        generators=vulnerability_suite_generator_registry.generators(),
        max_scenarios=40,
        seed=42,
    )
    Path("tests/suites/scan-v1.json").write_text(suite.model_dump_json(indent=2))


asyncio.run(main())
```

`Suite` is a Pydantic model, so `model_dump_json` is the whole serialiser. If you already ran a scan, the suite is on the result — `result.suite.model_dump_json()` — and no regeneration is needed.

Write it with `indent=2`. A one-line JSON file turns every regeneration into an unreviewable diff; an indented one shows you which scenarios changed.

## Load it back

```python
from pathlib import Path

import giskard.scan  # noqa: F401  — registers the scan prompt namespace
from giskard.checks import Suite

suite = Suite.model_validate_json(Path("tests/suites/scan-v1.json").read_text())
result = await suite.run(target=my_agent)
```

:::danger[Import `giskard.scan` before you run a loaded suite]
That unused-looking import is load-bearing. Scan scenarios reference their prompt templates by namespace — `prompt_path: "giskard.scan::scenarios/llm01_indirect_injection.j2"` — and the namespace is registered as a side effect of importing `giskard.scan`. Without the import, `Suite.model_validate_json` succeeds, and the run then fails with `KeyError: 'giskard.scan'` wrapped in a `WorkflowError: Step processing failed`.

It bites precisely where you would not look for it: the replay script only needs `giskard.checks` to load and run a suite, so the import is the easiest line to drop when tidying up. Keep it, with the `noqa` comment explaining why.
:::

Deserialisation is otherwise strict. Every polymorphic node — checks, interactions, input generators — carries a `kind` discriminator, and an unknown `kind` fails validation with `Kind <name> is not registered`. In practice that means a suite generated by a newer library version will not silently half-load into an older one.

## What the file does and does not contain

The suite holds scenarios: prompts, generator configuration, checks, and tags. It does **not** hold:

- **Your target.** A generated suite has no target attached; you pass one to `run`. That is the feature, not a gap: one suite, any agent.
- **The judge model.** Judging happens at run time against whatever `set_default_generator` is configured with. Change the judge model and the same suite can return a different pass rate.
- **The knowledge base.** A quality suite embeds the retrieved context in its scenarios, but the `KnowledgeBase` object itself is not part of the file. Version the documents alongside the suite.

So a suite pins the *questions*, not the *verdicts*. Two of the three inputs to a run still live outside the file.

## Version it like test code

Commit the JSON next to your tests and treat regeneration as a deliberate, reviewable act.

```
tests/suites/
  scan-v1.json        # generated 2026-03-11, seed 42, max_scenarios 40
  quality-v1.json
```

What to keep alongside it, because none of it survives in the file:

- the `description` and `languages` you generated from — a reworded description produces a materially different suite;
- `seed` and `max_scenarios`;
- the `giskard-scan` version, since generator defaults and prompts change between releases.

A short generation script checked in next to the suites records all of it, executably. That is preferable to a comment.

Regenerate when the agent's scope changes, when you bump `giskard-scan`, or on a slow cadence to widen coverage — not on every build. Bump the filename (`scan-v2.json`) rather than overwriting, so an unexpected pass-rate jump can be traced to the suite that caused it. Keep the old file until you have run both against the same agent and know what moved.

## Export results for CI

The suite is the input you version; JUnit XML is the output your pipeline reads:

```python
result = await suite.run(target=my_agent)
result.to_junit_xml("scan_results.xml")
```

One `<testsuite>`, one `<testcase>` per scenario, with failures, errors, and skips counted separately and each check's details attached. GitHub Actions, GitLab, Jenkins, and CircleCI all render it natively, which gets you per-scenario history without storing anything else.

Pair it with the raw result when you want the full conversations — `result.model_dump_json()` keeps every trace, at a much larger file size. Upload that as a build artifact rather than committing it.
